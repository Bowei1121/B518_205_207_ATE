## 2. 三方責任與已確認流程

上位機決定物料、治具、條碼與開測時機；橋接操作 KVM／HID、辨識畫面並回報；Log Solution 像儀器一樣，管理本輪來源、通道結果、期限、待確認及交付狀態。

```text
READY，等待新輪（可以保留前輪結果）
→ 上位機完成測試前準備
→ 開始監控命令被接受，立即鎖定本輪、禁止重複開始
→ BUSY／準備中，建立舊檔基準
→ BUSY／監控中，橋接確認本次監控就緒
→ 上位機觸發 ATE
→ Log 觀察到可信活動／有效結果，更新通道及色帶
→ 全部配置位置終局且無待確認
→ READY／完成，或 READY／人工停止
→ 橋接完成同輪、容量、影格穩定性與格位完整性驗證後交付
```

PREPARING 可以很短，不要求橋接一定看過它；開測前仍必須可靠觀察到 MONITORING。不能只看 BUSY 文字判定可開測，也不能以 MONITORING 或按鍵成功推定 ATE 真的開始。

## 3. READY／BUSY 與六種狀態

| 狀態 | HMI | 已確認意義 |
| --- | --- | --- |
| STANDBY | READY／待命 | 可接受新輪，沒有可交付的本輪結果 |
| PREPARING | BUSY／準備中 | 已接受本輪，但來源準備尚未完成；不得開測 |
| MONITORING | BUSY／監控中 | 來源已就緒，可讓上位機觸發 ATE；不是 ATE 已開測 |
| REVIEW | BUSY／待確認 | 衝突、警報或啟動失敗需要人員處理；橋接通知上位機報警並暫停 |
| COMPLETE | READY／完成 | 完整結果可交付；不代表全 PASS |
| MANUAL_STOP_COMPLETE | READY／人工停止 | 人工停止後完整結果可交付；須明確回報人工停止原因 |

結果色帶是各產品狀態，四格標記是整輪／儀器狀態；排數標記只表示一排或兩排，左右定位點只處理位置、方向及比例。REVIEW 是異常待處理的共同訊號，不直接辨識根因、不代表產品 FAIL；實際原因須顯示並保留診斷。

六種圖樣使用同一 2×2 黑白標記；原四碼保留，人工停止新增 0011 已獲使用者確認，準備中配套配置為 0101。精確位元、取樣規則及跨專案版本限制以交接文件為準。

## 4. 人工停止與同輪性

- 保留 PASS／FAIL／NOTEST／TIMEOUT 等已定案結果，只把未完成格改 STOPPED；HMI 通道與色帶都保留 STOPPED，不轉成 FAIL。
- 保留整輪人工停止原因，不能只靠某格 STOPPED 推測；即使每格已有終局結果，仍須能辨識人工停止。
- 來源尚未建立也立即停止，依配置形成完整格位；延遲來源準備不得覆蓋結果或重啟監控。空結果或缺格不算完整。
- 無待確認後才 MANUAL_STOP_COMPLETE；待確認事項尚未處理時 REVIEW 優先。
- 橋接尚未看見本次 MONITORING，就人工停止或準備逾時：回報需人工核對，不自動交付、不自動重測；確認警報不能替代同輪證據。
- 這些需人工核對的情況，操作員核對並取消本輪、保留紀錄；排除問題後明確開始新輪，不提供強制交付不確定結果的捷徑。
- 操作員決定重工範圍；不因人工停止就抹除全輪證據。已可靠保存、已確認同輪結果的正常重傳政策不變。
- 快照、畫面、Session／audit 稽核重建要一致；不能假造一般完成事件掩蓋人工停止。

## 5. 開始期限、測試活動與到期先後

FCT start 先採 120 秒，從接受開始監控起算、包含來源準備時間；後續依現場實測調整。必須更新實際被選取的已存 profile，不是只改 migration 預設。DFU／BT 不因此全部改成 120 秒。

整輪到開始期限都沒有可信活動，也沒有有效結果時，停止收集、未開始格定案為 NOTEST，顯示未偵測到測試開始警報，維持 REVIEW；人員確認且無其他待確認後，才可交付。若橋接未曾見本次 MONITORING，則仍按第 4 節人工核對並取消，不因警報確認而自動交付。

部分位置已有活動／結果時，不套用整輪完全無開始警報，未開始位置沿用各格既有期限政策。已開始後的測試期限與整輪監控上限仍保留，不被新的開始警報取代。

到期限時先判 deadline，再讀該次來源；若期限前程式尚未接受可信證據，不用到期後讀到的資料或來源自報時間挽回已到期狀態。期限前已接受的結果與活動保留。

TESTING／COMPLETING 或可信本輪測試結果可以證明某格已有活動；不推論全部通道都已開始。快速完成或只有結果檔的平台可以沒被觀察到 TESTING 就完成；WAITING／NOTEST／TIMEOUT／STOPPED 不單獨作為 ATE 開始證據。未觀察到開始不是已證明 ATE 當機。

## 6. 啟動失敗與復位

前置配置／路徑驗證失敗，與本輪已接受後來源建立失敗，都顯示 REVIEW／異常待確認；橋接通知上位機報警、暫停，不開測、不交付殘留結果。

- 尚未接受本輪：只記失敗請求及 App 異常，不補造輪次、不把錯誤掛到上一輪。
- 已接受本輪：停止並保留失敗輪次、原因與診斷，不造產品 FAIL，不顯示人工停止完成。
- 人員排除問題、確認並復位；已建輪次就取消該輪，未建輪次就結束失敗請求，保留紀錄後才 READY。
- 不自動重試、不自動啟動 ATE；下一次明確觸發才建立新輪。關閉錯誤視窗不等於復位。
- 復位不代表刪除證據、採用未知同輪結果，或自動重啟 ATE／操作治具。

## 7. 視窗前景與幾何

開始監控、觀察到 TESTING、結果更新及整輪完成時提升視窗；同批事件合併，不因輪詢反覆提升。不永久 topmost，不強制鍵盤焦點；橋接需要畫面時可由自身自動化點 Dock 恢復。實際 ATE 焦點須原生桌面驗收。

移除 KVM RESULT 字樣，左定位點移到第一格色帶正上方；保留右定位點、排數格、狀態格、色帶位置與顏色。左定位點保留不對稱內嵌白格與留白，不裁切、不重疊；精確座標須量測後凍結。

上方定位點不能保證偵測所有只遮色帶的視窗形狀；橋接仍須逐格可讀性、排數、完整性與影格新鮮度驗證。先部署支援新舊幾何／新圖樣的橋接，再部署 Log Solution 1.2。

## 8. 交由 KVM_Log 接續的事項

採 monitor_start 確認 Log 就緒、check_start 確認實際通道活動、check_finish 取得整輪結果。check_start 若已取得完整可交付結果，可以直接交付，不要求再查一次；活動回覆不消耗最終結果，每請求只回一筆。

人工停止需保留獨立完成種類，未見本次監控就緒須回需人工核對。完整 TCP 欄位、協定版本、舊 check 遷移及 LabVIEW typedef／VI 配對屬 KVM_Log 接續工作，不在本專案新增 TCP server。顯示契約 1.2 與 TCP 協定版本不能混為一談。

## 9. 與既有決策／程式的關係

- 延續 ADR 0001 的單工站整輪，釐清監控開始與實際測試開始的時間差。
- 延續 ADR 0004 的讀檔停止／放行分離、待確認阻擋；補充開始警報與人工停止交付政策。
- 延續 ADR 0005 的四個主要 module、Python／Tk 與逐步遷移；不順便重寫 UI 或查詢。
- ADR 0006 的未知來源候選處置保持；橋接無法證明畫面同輪而取消，與本地未知來源候選判 FAIL 是不同問題。
- ADR 0007／0008／0009 的資料保護、完整保存才關閉及雙語紀錄保持。結果可交付不新增 audit／封存完成前置。
- 變更現行顯示契約 1.1 的四種狀態與人工停止不交付行為；目前程式仍為 1.1，需求確認不代表新行為已上線。

本輪唯讀程式查核仍見 `kvm_display_contract.py` 的 CONTRACT_VERSION=1.1／四狀態，及 `monitoring_round.py` 快照只於 COMPLETED 放行；後續需同步 stop、來源準備、快照、顯示及稽核重建，不能只改圖樣。既有未提交 UI／測試暫稿不因本次討論自動採納。
