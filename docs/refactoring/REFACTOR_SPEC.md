# B518 Log Solution 正式重構規格

日期：2026-09-30（Asia/Taipei）。範圍：將已完成客戶展示的 MVP 演進為跨產品專案的通用 PCBA ATE Log 監控工具。

需求與四個主要模組分工已由使用者確認。本規格綜合需求訪談、領域詞彙、ADR 0001～0006、重構設計基準及現有程式與測試；不代表功能已實作或驗收通過。主要行為測試接口與 7 個代表案例已由使用者於 2026-09-30 明確確認，確認紀錄見 Ticket 01 及下方「Testing Decisions」。未知同輪來源政策於 2026-10-06 決定，行為交付由 Ticket 18 驗收。

## Problem Statement

現有 App 已能在 macOS 讀取 DFU、FCT 及 BT 測試 Log，向現場與上位機提供產品結果，完成 MVP 展示。但產品型別改變時，設備與治具的測試容量會不同；測試平台改變時，Log 路徑、檔案格式、位置編號與批次資訊也會不同。目前工站、容量、平台選擇、部分判定與畫面組裝互相牽連，變更往往需要修改多處並重新打包。

客戶希望現場人員只選擇專案與機型，避免逐項設定。工程師則需要透過畫面準備、驗證與部署配置，並能在新增格式時集中開發解析模組。工具也需要支援已知最多二十片、每輪不必放滿的測試方式，避免空位讓監控無限等待；發現結果矛盾或整輪逾時時，需由現場確認，並讓上位機知道此時不得繼續動作。

## Solution

保留 Python／Tk 與現有 macOS 打包方式，以測試配置、平台資料來源、監控輪次、桌面介面四個主要模組分工。平台模組理解自己的 Log，輪次模組統一管理共同流程，介面呈現同一份輪次狀態。

現場以「專案：B482；機型：FCT」等選項開始一輪監控；工程師透過進階畫面編輯及匯出配置。已支援平台的容量、路徑、位置對應與逾時可只更新配置，新 Log 格式隨 App 重新發布。

KVM 色帶每排固定十格，容量超過十片時使用第二排，超出容量的位置為黑色。固定定位點旁另有獨立黑白標記，表達待命、監控中、本輪完成與待確認。全通道有結果即停止讀檔；未決確認處理完才供上位機取用。整輪逾時停止收集、保留已有結果並要求確認，不自動略過衝突。

## User Stories

以下各項均以「角色希望獲得的能力與目的」描述，對應後續接口及驗收條件。

1. 作為現場操作員，我希望只選擇專案與機型，以便不用理解平台格式、路徑與容量設定。
2. 作為現場操作員，我希望重新啟動後能恢復有效的選擇與配置，以便減少重複操作。
3. 作為現場操作員，我希望以開始按鈕或既有快捷鍵啟動監控，以便在測試軟體取得焦點時也能操作。
4. 作為現場操作員，我希望監控中重複開始不會重設本輪，以便保留已取得的狀態與結果。
5. 作為現場操作員，我希望啟動前發現缺少路徑或無法讀取時能看到原因，以便由工程師修正。
6. 作為現場操作員，我希望啟動前已有的資料不被當成本輪結果，以便上位機不會讀到上一批產品。
7. 作為現場操作員，我希望設備容量與本輪實際投入數量分開，以便治具未放滿時仍能完成一輪。
8. 作為現場操作員，我希望有效測試活動出現時顯示測試中與可信 SN，以便知道各位置的進度。
9. 作為現場操作員，我希望等待最終結果時能區分測試中與收尾中，以便理解當前進度。
10. 作為現場操作員，我希望程式依平台證據判定最終結果，以便單一測項 PASS 不會被誤當整機 PASS。
11. 作為現場操作員，我希望未開始的通道等待逾時後自動顯示 NOTEST，以便不必逐一處理空位。
12. 作為現場操作員，我希望已開始但未完成的通道能顯示 TIMEOUT，以便區分未測與測試未正常完成。
13. 作為現場操作員，我希望個別通道逾時不會抹去其他結果，以便其餘通道能正常收尾。
14. 作為現場操作員，我希望整輪到達監控上限就停止讀檔並報警，以便避免無限等待。
15. 作為現場操作員，我希望整輪逾時時已完成結果保留，以便不用重新確認正常完成的產品。
16. 作為現場操作員，我希望衝突彈窗顯示位置、SN、原結果、新結果與來源時間，以便確認該通道的真實結果。
17. 作為現場操作員，我希望可以保留原結果或採用新結果，以便處理已確認情境中的矛盾。
18. 作為現場操作員，我希望確認某通道時其他通道仍繼續監控，以便不阻塞正在測試的產品。
19. 作為現場操作員，我希望全通道有結果後就停止收集，以便一輪有明確結束界線。
20. 作為現場操作員，我希望確認警報與衝突後才放行結果，以便上位機不會使用尚有爭議的資訊。
21. 作為現場操作員，我希望可以停止監控且已完成結果保留，以便中斷本輪時不失去已取得資訊。
22. 作為現場操作員，我希望頂部色帶始終可見且產品明細能捲動，以便最多二十片也能查看而不移動上位機取色位置。
23. 作為現場操作員，我希望介面保持高對比並能看見結果與警報，以便在現場容易辨識狀態。
24. 作為工程師，我希望透過進階畫面編輯配置，以便理解各設定而不必手寫文字檔。
25. 作為工程師，我希望匯出、匯入及重新載入後保留等價配置，以便將確認好的設定部署到現場。
26. 作為工程師，我希望取消編輯不改動原配置，以便試調時不誤套用未完成設定。
27. 作為工程師，我希望配置錯誤在套用或開始前被指出，以便避免錯誤位置、路徑或逾時造成誤判。
28. 作為工程師，我希望改容量、路徑、位置對應或逾時時只更新配置，以便降低現場 App 更新成本。
29. 作為工程師，我希望同一專案與機型若有設備差異，可由部署時設定適用配置，以便操作員仍維持簡單選擇。
30. 作為工程師，我希望依平台實際資料到達時間設定等待值，以便僅完成後匯出檔案的平台不會過早被判未測。
31. 作為開發者，我希望新增格式的變更集中於平台模組、註冊與測試，以便不重複修改 UI 或共同輪次規則。
32. 作為開發者，我希望平台特有的 SN、日期、結果與批次證據由該平台封裝，以便格式差異不散布到其他模組。
33. 作為開發者，我希望能以樣本 Log 與可控制時間驗證一輪，以便不依賴設備或真實等待時間。
34. 作為開發者，我希望搬移模組時既有解析案例仍能重現，以便辨識非預期行為變更。
35. 作為維護工程師，我希望查到配置、來源、逾時原因與人工選擇，以便定位問題及重現異常。
36. 作為上位機整合工程師，我希望固定定位點與格位提供穩定參考，以便不使用 OCR 也能讀取結果。
37. 作為上位機整合工程師，我希望獨立標記區分監控中、待確認與完成，以便決定何時可以取用本輪結果。
38. 作為上位機整合工程師，我希望容量外黑格與容量內 NOTEST 不同，以便知道位置未配置或本輪未測。
39. 作為上位機整合工程師，我希望待確認時暫停本輪後續動作，以便不把有爭議的結果當作正常完成。
40. 作為上位機整合工程師，我希望事後異常不自動觸發重做動作，以便保持已完成的設備處理流程一致。
41. 作為發布工程師，我希望模組搬移後 App 仍能通過既有打包與相容性檢查，以便維持原有 macOS 部署能力。
42. 作為專案負責人，我希望 App 與更新後上位機共同驗收，以便通用監控能力能在實際 KVM 畫面中運作。

## Implementation Decisions

### 1. 決策層級

下列產品行為與四模組分工是已確認決策。接口的責任、資料語意與不變條件是本規格的實作契約；方法命名、套件目錄及具體資料型別由實作決定。配置版本編碼、KVM 像素規格、匯入遷移細節及時間邊界處理屬待落地的工程細節，須以可驗證案例定義，不得自行改變已確認產品規則。

### 2. 既有行為保護、模組搬移與新增功能

| 類別 | 必須保護或交付的內容 |
| --- | --- |
| 既有解析保護 | Atlas 可信 SN 欄位、首次可信 SN 鎖定、active 至 archive 的流程與 SN 讀取失敗；B482 TestData／CaseInfo 格式、第二個 SNRead 動作欄位、增量及半筆記錄；RS-WMT 單產品 CSV／Log、日期核對、排除摘要檔、單測項 PASS 不等於整機 PASS |
| 既有語意保護 | B482 空 SN FAILED → NOTEST 是歷史基準，已由 ADR 0006／Ticket 18 使用者決策取代為產品 FAIL；RS-WMT 明確 Fail 沒有 SN 仍為 FAIL。歷史資料快照、檔案穩定性判讀、最終結果不被後續進度事件降級，不能因共用化而遺失 |
| 既有操作保護 | 快捷鍵、手動開始／停止、路徑檢查、設定草稿與儲存／取消、淺色高對比、不持續置頂、結果前景顯示、每輪紀錄與 macOS 打包檢查；與新流程衝突處以本規格為準 |
| 模組搬移 | 將格式與資料探索集中於平台資料來源；將共同狀態與時間規則集中於監控輪次；畫面經統一接口取得狀態，不直接存取具體平台監控器內部結果或人工覆核方法 |
| 新增／明確變更 | 專案＋機型操作入口、工程師配置畫面及匯入匯出、配置容量與來源位置映射、最多二十片、十格／兩排、新黑白標記、可捲動明細、各通道等待逾時 NOTEST、整輪上限、共同人工確認流程、停止收集與放行分離 |
| 不應原樣保護的 MVP 行為 | 工站固定 7／6／4、七格色帶、整輪無活動自動 TIMEOUT、全通道終態後再持續觀察三秒、RS-WMT 缺資料永久等待，以及單純依檔案路徑不同觸發的覆核，不可直接當成新版驗收標準 |

### 3. 模組接口

| Module | 呼叫端需要知道的 Interface | 必須隱藏的 Implementation |
| --- | --- | --- |
| 測試配置 | 列出可用專案與機型；讀取與驗證配置；從草稿套用、匯入與匯出；提供本輪使用的配置快照及可讀錯誤 | 儲存格式、配置版本、舊偏好相容與平台參數布局；不解析產品結果 |
| 平台資料來源 | 依配置準備來源快照；讀取新活動與候選結果；提供可用批次證據及來源診斷；停止收集 | 檔案搜尋、編碼、日期、半寫入緩衝、穩定等待、平台位置編號、特有 SN 與結果證據 |
| 監控輪次 | 啟動／停止本輪；執行一次監控推進；取得一致狀態快照與事件；提交衝突選擇或確認警報 | 通道狀態、共同期限、候選結果處理、收集停止、人工確認與結果放行；時鐘、排程及紀錄經內部接口注入 |
| 桌面介面 | 選擇配置並提交操作；呈現輪次快照；呼叫配置編輯／匯入匯出及人工確認 | Tk 元件、布局、捲動、彈窗、快捷鍵、前景顯示與 KVM 繪製 |

監控輪次是操作流程的主要 Interface。平台 Adapter 可更換，但呼叫端不需要知道其內部格式；可重用現有一次輪詢、時鐘與事件方式，避免建立只轉發呼叫的淺層包裝。

平台資料來源的觀察資料至少表達：來源位置、可信 SN（若有）、測試活動或最終候選結果、來源時間、來源識別及可取得的批次證據。來源時間與檔案複製時間分開；沒有證據的欄位須保持未知，不能捏造。平台證據與共同輪次規則經此接口分工，不統一成「空 SN 都等於 NOTEST」。

### 4. 配置與容量

1. 操作員只選專案與機型。機型是 DFU／FCT／BT 工站類型；平台與容量由工程師準備的適用配置決定。
2. 配置涵蓋專案、機型、已支援平台識別、容量、Log 路徑、來源位置至顯示位置的對應、開始等待時間、個別測試上限及整輪監控上限。
3. 支援本次需求範圍的一至二十個有效位置；容量不是每輪預計投入數量。來源編號可為 Thread、Slot 或其他平台標記，顯示位置為一至容量，映射由配置及平台能力共同驗證。
4. 不能只增加 UI 行數而保留解析器的四通道或特定產品硬編碼。平台本身未提供的容量或格式能力，不得因配置填入數字就宣稱已支援；不相容配置須可辨識。
5. 工程師透過進階畫面編輯草稿，驗證後套用或匯出；取消不改原配置。匯入與匯出後可恢復等價設定，失敗不能以半套設定替換原有效配置。
6. 配置需能識別版本，並使未知平台、缺少必要欄位、非法容量、重複／越界映射、非正整數逾時與不相容版本等錯誤可被指出。具體版本格式及相容策略於實作定義。
7. 工程師可能在另一台電腦製作配置，編輯／匯入的結構檢查與部署後的實際路徑可讀性檢查須區分；真正開始前不得把空白路徑當目前目錄。
8. 本輪綁定開始時的配置快照；編輯或匯入不得悄悄改變進行中的容量、映射或時間規則。配置更新何時進入畫面選單由介面設計落實。
9. 同一專案＋機型若出現設備差異，由工程師部署適用配置處理，不將此例外轉成操作員日常的第三個選項。
10. 已支援平台的參數更新不重打包 App；新格式開發 Adapter、註冊及樣本驗證後隨 App 發布，不要求動態載入外部解析器。

### 5. 輪次與時間規則

一台 App 一次監控一個工站，各位置屬於同一測試輪次。治具本輪開始後鎖定，不支援本輪中途各位置獨立換料進入下一輪。

| 期限 | 起算點 | 到期處理 |
| --- | --- | --- |
| 各通道共同開始等待 | 接受操作員按下開始監控的時刻 | 沒有活動或最終結果的有效位置定為 NOTEST；已有活動或結果者不因此被重設 |
| 個別通道測試上限 | 首次觀察到該通道可信測試活動 | 該通道未完成則 TIMEOUT；COMPLETING 也計入；其他通道繼續 |
| 整輪監控上限 | 接受開始監控的同一時刻 | 停止讀檔、已取得結果保留、未開始者 NOTEST、已開始未完成者 TIMEOUT，產生一次待確認警報 |

期限從使用者已確認的起點計算，不因第一個通道開始、收到新進度、建立快照完成或彈窗而重新倒數。啟動準備不能阻塞 UI，使期限與警報失去作用；計時使用可注入的穩定時鐘，來源日期判讀另行處理。

開始等待造成的 NOTEST 表示「期限內未觀察到測試」，不是證明治具物理空位。紀錄需區分此推定與平台明確回報的未測。只有最終匯出檔的平台，工程師必須依完整測試及匯出時間設定等待值，不假定即時 Log 必定存在。

新規則不保留全通道有結果後額外三秒輪詢；檔案本身尚未寫完的穩定等待仍由平台處理。資料被接受、期限到達的同次推進先後需在實作中明確定義並測試，不以檔案排序或不同 thread 時序決定結果。

### 6. 結果、衝突與放行

1. 通道流程保留 WAITING、TESTING、COMPLETING、PASS、FAIL、NOTEST、TIMEOUT 與人工停止的 STOPPED。產品結果與整個程式的狀態分開。
2. 全通道已有最終結果（包含 NOTEST／TIMEOUT）即停止收集。沒有待確認事項時才能顯示本輪完成；資料執行緒停止不能自行代表已放行。
3. 監控仍在收集時觀察到同通道結果、SN 或其他結果證據矛盾，進入共同人工確認流程。僅來源路徑不同但內容一致的重複輸入，需與結果矛盾區分；重複資料不應反覆發送同一結果事件。
4. 確認資料涵蓋位置、可取得的原／新 SN、原／新結果、來源識別與來源時間；缺少資訊顯示未知，不以複製時間冒充測試時間。
5. 現場可保留原結果或採用新結果，記錄選擇與時間。確認只適用於所選衝突，不能順帶接受全部候選結果。
6. 等待確認時其他位置繼續收集與計時；彈窗不遮住程式標記。多項衝突不能相互覆蓋或因一項確認就被清除，呈現方式由介面落實。
7. 整輪逾時停止收集並只產生一次警報；程式為待確認。警報確認不等於接受衝突，所有既有必要確認完成才放行，不再增加人工確認倒數。
8. 全通道結果齊全但仍待確認時，不繼續讀新 Log。停止前已捕捉的候選資料仍可供人工選擇，不能因停止收集而遺失。
9. 以監控實例識別操作、狀態與事件；舊實例排隊事件不能更新新輪畫面或結果。來源無法確認同輪時禁止人工採用，候選使該 slot 判為 FAIL；政策及操作紀錄見 ADR 0006 與 Ticket 18。
10. 人工停止保留已完成結果，未完成位置維持既有 STOPPED 語意；停止不自動變成正常本輪完成，也不補為空位 NOTEST。
11. 停止後不新增遲到資料觀察期，也不承諾偵測之後的檔案變更。若因已知資訊或人工操作呈現事後異常，不能自動要求上位機重做已執行動作。

### 7. 桌面與上位機顯示契約

| 程式標記 | 語意 | 上位機處理 |
| --- | --- | --- |
| 待命 | 尚未進入可取用的本輪完成狀態，包含未啟動或人工停止後的非完成狀態 | 不將保留在畫面的舊色帶當本輪完成 |
| 監控中 | 正在準備／收集本輪資料，且沒有待確認事項 | 等待，不取用部分結果作為整輪完成 |
| 待確認 | 有衝突或整輪逾時警報，可能仍在收集其他位置，也可能已停止讀檔 | 暫停該輪後續動作 |
| 本輪完成 | 收集已停止、所有有效位置有結果，且沒有未處理的必要確認 | 取用本輪產品結果 |

1. 容量一至十：固定一排十格；十一至二十：固定兩排各十格。第一排對應位置一至十、第二排對應十一至二十，容量外格子固定黑色。
2. 容量內的 WAITING、TESTING、COMPLETING、PASS、FAIL、NOTEST、TIMEOUT 等採既有明確色碼；不得把未放滿的位置塗成容量外黑色。
3. 色帶固定在主畫面頂部且不隨明細捲動；SN／狀態明細可捲動以容納二十筆。
4. 固定定位點用於找到畫面與確認方向，獨立黑白標記表達程式狀態。二乘二黑白格為已選方向的示意；像素尺寸、間距、縮放容差、pattern 或取樣門檻要由 App／上位機共同落地驗證。
5. 標記固定可見、不閃爍且不被人工確認視窗遮住。辨識不明的畫面不能被宣稱為本輪完成；上位機只依可靠的完成標記取用。
6. 產品色帶與程式標記由同一輪次狀態產生；更新需避免出現上一輪完成標記搭配新輪初始化色帶的可取用畫面。
7. 全面採新排列，上位機同步更新，沒有舊七格相容模式。組合驗收包含不同容量、確認期間、正常完成及整輪逾時。
8. 維持現有高對比淺色、快捷鍵與不持續置頂策略；視窗尺寸依新布局驗證，不能直接保留固定工站高度而使色帶被裁切。結果前景顯示與確認窗口不得導致標記不可見。

### 8. 紀錄與部署

每輪保留既有的設定、事件、結果、時間與來源紀錄，增加或明確表達配置版本與本輪快照、推定 NOTEST／平台 NOTEST 的原因、警報、候選結果與人工選擇，以及收集停止和結果放行的不同時刻。紀錄與 UI／KVM 使用同一輪次狀態，原始 Log 備份不在本次需求中。

保留現有 Intel 與 Apple Silicon 各 macOS 目標的打包流程、Python／Tk 前置檢查、測試門檻、適用的 bundle 架構／最低版本／依賴檢查、簽章驗證與校驗資訊。模組搬移時同步調整打包引用，配置與所需資源必須能被部署後 App 正常使用。靜態檢查不能代替目標機啟動及現場測試。

### 9. 遷移安排

1. **建立基準**：保留可用版本，以現有匿名化樣本、解析案例與回放方式記錄應保護的行為；將本規格的預期變更與尚未驗收限制另列。
2. **整理配置與平台接口**：移出格式、來源探索與位置映射，先證明既有資料可經新分工得到同樣解析。必要時以新舊接口短暫並存逐批遷移，維持各批可驗證。
3. **整理共同輪次**：將狀態、時間、停止收集、衝突與放行集中管理，新增配置容量、各通道 NOTEST 與整輪上限。以模擬時鐘完整驗證正常與異常流程。
4. **接通完整操作**：工程師畫面編輯並匯出／部署配置，現場選專案與機型完成一輪，顯示新色帶、黑白狀態與明細；同步接上上位機辨識。
5. **整合與發布驗收**：App／上位機組合測試、既有測試調整與新增案例、macOS 打包檢查及目標機驗收；移除已無呼叫端的舊流程。

遷移是內部安排，最終交付要能完成端到端流程；不以四個模組各完成一層當成四個可驗收產品。明確保留的政策分支應留出可實作位置，在定案前不宣稱該分支完成。

## Testing Decisions

### 1. 主要測試接口與確認狀態

**已確認接口：**以「配置啟動一輪 → 提供樣本 Log／推進模擬時間／輪詢 → 取得通道結果及程式狀態 → 提交人工選擇／確認警報 → 觀察停止收集及是否可取用」作為主要行為測試接口。測試經監控輪次對外 Interface，優先延續現有一次輪詢、可注入日期／單調時鐘、事件 callback、暫存來源及紀錄位置的方式。使用者於 2026-09-30 明確接受此公開接口與 Ticket 01 所列 7 個代表案例，作為後續主要行為測試範圍。

實際行為測試以 Ticket 02 建立的共同輪次對外接口為測試邊界；Ticket 01 的確認不代表該接口已實作，也不核准提前執行後續重構。這項接口確認不包含未知同輪來源政策；該政策已由使用者於 2026-10-06 決定並記入 ADR 0006，Ticket 18 負責行為驗收。

### 2. 測試原則與補充接口

- 驗證可觀察結果、狀態、事件、配置與人工選擇，不驗證私人方法、thread 數量、類別繼承或搬移後的檔案布局。
- 測試與 UI 使用同一個輪次 Interface；時鐘、樣本與儲存位置可替換，無須測試設備、實際長時間 sleep 或 Tk 畫面才能跑主要案例。
- 配置的驗證、匯入／匯出與取消編輯經配置 Interface 補充測試，觀察等價配置及失敗後原值保留。
- 各平台以已知樣本保留格式回歸測試，重點為欄位證據、半寫入、檔案穩定性與來源資訊；重複的共同流程移至輪次測試，不在每個 Adapter 再複製一套逾時測試。
- Tk／KVM 補充測試驗證可見格位、黑白標記、捲動、彈窗與快捷鍵；上位機透過實際或受控 KVM 畫面完成取用契約驗證。
- 打包檢查保留獨立驗證層。測試通過、靜態 bundle 檢查、目標 macOS 實機驗收分別記錄，不混稱全部相容。

### 3. 現有可沿用資產

已有 Atlas SN 鎖定及 archive 解析、歷史檔排除、B482 空 SN NOTEST、CaseInfo 實機格式與半筆資料、逾時與完成結果保留測試。RS-WMT 已有日期與位置證據、無 SN Fail、摘要檔排除、半寫入、增量 Log、非整機 PASS、舊資料排除與穩定性重置案例，另有只讀原始資料、暫存來源及模擬時鐘的單輪回放工具。

介面測試已有高對比、路徑檢查、設定儲存／恢復／取消、快捷鍵、前景顯示與非持續置頂驗證；打包已有架構、最低系統版本及依賴檢查案例。搬移後重用這些先例，但固定七格／工站容量、開始逾時全部 TIMEOUT、不同平台直接忽略所有衝突等預期須依新版規則調整。

外部實機資料來源、目錄盤點、現有回放入口，以及從樣本衍生模擬情境的規則，見 [實機測試資料與回放使用指南](TEST_DATA_GUIDE.md)。原件保持唯讀，回放使用暫存副本；實機格式保護、合成情境與現場驗收分別記錄，不因有樣本就宣稱匿名化樣本包或重構驗收完成。

### 4. 可驗證的驗收條件

| ID | 情境 | 必須觀察到的結果 |
| --- | --- | --- |

| AC-02 | 匯出後匯入、取消編輯或匯入錯誤 | 有效配置可等價恢復；取消或失敗保留原設定；錯誤可讀 |
| AC-03 | 非法容量、重複／越界映射、未知平台或非正整數逾時 | 配置被拒絕，不啟動本輪；缺少／不可讀實際路徑於開始前被指出 |

## Out of Scope

1. 同一 App 同時監控多工站、多設備，或治具本輪鎖定期間各位置獨立換料重測。
2. 換用新的 UI 技術、平台，或加入 Arduino、TCP／USB 控制、鍵盤滑鼠操作、截圖等測試設備控制功能。
3. 舊七格 KVM 相容模式，以及長期同時維護新舊兩套排列。
4. 動態載入外部解析器、規則腳本或外掛商店；新格式仍隨 App 發布。
5. 全通道有結果後的額外監聽觀察期、停止後新資料的自動接受，以及人工確認等待逾時計時器。
6. 上位機已完成處理後自動重做動作；本規格中的異常提示不擴張成補救設備控制流程。
7. 原始 Log 自動備份、雲端集中管理、遠端診斷與使用者帳號／權限系統；本次進階畫面分工不等於已要求密碼或身分驗證。
8. 超過二十片的顯示與容量需求、目前沒有樣本的新平台格式，以及未被儀器支援的實際硬體容量。
9. 替使用者決定來源不確定的人工採用政策；該分支屬明確延後決策。
10. 本次規格產出不包含修改 App、執行重構、發布遠端議題或自動拆票。

## Further Notes

### 1. 明確保留的關鍵決策

「來源無法確認是否屬於同一輪時，是否允許人工採用結果」由使用者於 2026-10-06 決定：一律禁止，涵蓋第一筆 final 與替換既有結果。依 ADR 0006，測試時間是最低來源證據，未知欄位不補造；SN 不作為最低證據，SN 讀取失敗的產品判定為 FAIL；證據不足、拒絕或沒有選擇時 Slot 判為 FAIL，操作、候選及時間寫入紀錄，不寫理由。這項決定取代 Ticket 01／04 先前將 B482 空 SN 且 FAILED 映射為 NOTEST 的行為。不得把現有 B482 跨批次接受或 RS-WMT 拒絕不同批次當作新版已確認通則。能確認同輪的衝突仍依 Ticket 10 處理。

### 2. 工程細節與發布限制

配置版本及舊偏好遷移、具體接口名稱、時間到期同次輪詢的先後、多項確認呈現、KVM 像素幾何與辨識容差屬實作細節。實作應記錄與驗證選擇，若選擇會改變本規格的產品規則，才補問該關鍵決策。

新平台若只能完成後匯出 Log，不保證提前看得到測試中或能判斷測試軟體當機。現有 RS-WMT 即時資料時機、Apple Silicon 打包與目標機實際部署仍有待驗項目；本規格未將既有文件中的候選建置流程視為已完成現場驗收。

上位機屬同步整合與共同驗收範圍；實作前需定位其程式、部署流程與負責者，不能以 App 畫面顯示正確代替上位機暫停／取用驗證。發布時需同步更新操作手冊、配置說明及部署注意事項，使現場文案符合新的 NOTEST、整輪警報與人工放行規則。

### 3. 最終完成標準

- 已支援平台只更新配置即可調整容量、路徑、位置及逾時，不需重新打包。
- 新格式變更集中於平台資料來源與其測試及註冊，不改 UI 或共同輪次規則。
- 保護既有解析，新增一至二十通道、NOTEST／TIMEOUT、人工確認與 KVM 規則均可重現驗證。
