# Log Solution 重構訪談摘要｜2026-09-29

## 資料來源與現況

- 本紀錄依本次 grill-with-docs 訪談、App README、既有專案摘要與提交 003632b 建立；不代表已讀取其他任務的完整對話。
- MVP 已完成客戶展示，使用者希望將獨立 Log 監控 App 模組化，成為跨產品專案使用的通用工具。
- 既有 App 支援 DFU、FCT、B482 BT TestData／CaseInfo 與 B518 BT RS-WMT，另有 KVM 結果顯示、快捷鍵、逾時與每輪紀錄。
- 程式已有 UI、監控核心、RS-WMT 與快捷鍵檔案；UI 直接組裝具體監控器，BaseMonitor 同時處理狀態、逾時、背景執行與 Session 儲存。
- 既有文件記錄 RS-WMT 即時 Log 時機與 M4 目標機驗收仍待確認；本次訪談未重新執行測試或現場驗收。

## 第一輪已確認

1. 重構範圍：跨 B518、B482 等產品專案使用的通用 Log 監控工具，不限於整理現有 B518 App。
2. 最常變更的需求：產品型別不同，一次測試的產品數量可能不同；測試平台不同，Log 存放路徑與格式也可能不同，需要對應解析器。
3. A（新增工站或格式）與 F（定位問題及驗證）是模組化帶來的好處；不能以此取代上述具體變動需求。
4. 先保有現今設計，日後有需要再修改；尚未授權在這輪訪談中改變程式行為。

## 第二輪已確認

1. 同時存在兩種數量差異：不同產品與治具的測試容量不同，同一配置每輪也可能未放滿。已知最大需求為同時測試 20 片。
2. KVM 結果顯示目標為每排最多 10 個產品，超過 10 個使用第二排；這是對第一輪「先保留現今設計」的明確範圍修正。舊七格辨識的遷移方式、未滿一排的格數尚未決定。
3. BT 是測試 PCBA 藍芽功能的工站；B482 與 B518 可能使用不同廠商的測試軟體平台，因此路徑與格式不同。現有相關儀器支援四通道、治具一次四顆，但希望可透過進階設定客製化，不能把 BT 的容量永久寫死為四。
4. 使用者偏好工程師提供預設配置、TE 僅調整部分欄位；客戶偏好工程師準備配置檔、現場只選擇配置以減少工作量。一般操作與進階配置的分工、開放欄位仍待確認，不能將其中一種偏好記成唯一決策。
5. 一台測試電腦上的 App 一次只監控一個工站；尚未決定該工站內是否允許各位置獨立更換產品並重測。

## 第三輪已確認（優先於前輪未決項目）

1. 為降低現場人工處理需求，某通道在等待期限內都沒有測試時，自動定為 NOTEST。截止時間、起算點與僅有最終匯出檔的平台如何配置仍待釐清；這是對保留既有判定行為的另一項明確調整。
2. 所有位置屬於同一輪，下一批重新開始監控。本輪測試開始時治具鎖定，人員與機械手臂無法觸碰產品，不設計各位置獨立換料重測。
3. 現場人員只需選擇「專案與機型」，不逐項設定。配置由工程師準備；「機型」具體指產品型號或測試設備型號尚待釐清。
4. 全部切換新 KVM 排列，同步更新上位機辨識，不維護舊七格相容模式。此處為已確認的設計方向，尚未執行上位機或 App 修改。

## 第四輪已確認（優先於前輪未決項目）

1. 按下「開始監控」後，每個通道共同開始等待倒數，不以第一個通道出現活動作為起算點。各配置的具體等待秒數與僅有最終匯出檔的平台設定尚未定案。
2. 專案是產品專案代號，例如 B518、B482；機型是 DFU、FCT、BT 三種測試儀器類型。操作員的選項為「專案：B482；機型：FCT」。
3. KVM 採固定每排十格：四片容量顯示一排十格，十二片或二十片容量顯示兩排各十格，超出配置容量的格子為黑色。目的為讓上位機方便分析結果。

## 第五輪已確認（優先於前輪未決項目）

1. 遲到資料或結果前後不一致時，要彈窗請現場人員確認，不採用「只記錄、不詢問」的建議。低人工介入仍是一般操作方向，結果衝突為明確例外；確認選項、監控持續期間與確認中的 KVM 狀態尚未決定。
2. KVM 色帶固定於頂部且始終可見，下方產品 SN 與狀態明細可捲動，以容納最多二十片而不要求二十列同時可見。
3. 已支援的平台若只修改容量、路徑、位置對應或逾時，只更新配置；尚未支援的 Log 格式需開發解析模組並重新發布 App，接受此發布方式。
4. 工程師透過進階設定人機畫面製作配置並匯出檔案供現場使用，不採文字範本作為主要配置製作方式。使用者認為畫面更親切，也較容易理解如何設定。

## 第六輪已確認（優先於前輪未決項目）

1. 衝突彈窗顯示位置、SN、原結果、新結果與來源時間，提供「保留原結果」及「採用新結果」，記錄現場選擇。
2. 使用者對「無法確認同輪的來源一律不得覆蓋」持保留態度，明確延後決定；不可把禁止跨輪覆蓋記為已接受的業務規則。
3. 全部通道都有測試結果後應停止監控，不為本輪額外觀察遲到資料。先前持續觀察至下一輪的建議撤回；停止後不保證偵測後續檔案變更。
4. 增加待確認狀態，上位機看到後暫停該輪後續動作，人工確認後恢復可取用狀態；若上位機已處理該輪，只作事後異常提示，不自動重做動作。停止監控後不新增資料監聽來實現此提示。
5. 使用者詢問能否以簡單 icon／定位點讓上位機辨識程式异常。本輪提出獨立黑白狀態標記的示意，固定定位點不隨狀態改變；標記格式與完成條件仍是提案，未定案、未實測。

## 第七輪已確認（優先於前輪未決項目）

1. 採用獨立黑白程式狀態標記，配合固定定位點供上位機定位與分析。
2. 衝突通道彈窗待確認時，其餘通道繼續收集；全部通道都有結果後停止讀取新 Log；所有待確認事項處理完才顯示本輪完成並供上位機取用。
3. 使用者在「仍有待確認事項」的步驟補充：需設計逾時時間，監控時間超過期限也要彈窗報警。這裡的計時範圍可能為整輪監控或等待人工確認，尚未釐清，不預設兩者相同，也不預設報警即放行。

## 第八輪已確認（優先於前輪未決項目）

1. 新增的逾時設定是「整輪監控上限」，從按下開始監控計時，超過期限仍未完成就彈窗報警；不選人工確認等待上限。
2. 使用者目前認為彈窗通常發生在檢測完成後。這是現場流程的理解，不取代前輪已確認的「某通道衝突可先彈窗，其餘通道繼續收集」；不可據此假定所有彈窗必定出現在整輪完成後。
3. 整輪逾時後的停止／繼續收集、未完成通道狀態與人工處置尚待確認。

## 第九輪已確認（優先於前輪未決項目）

1. 整輪逾時立即停止讀取新 Log，彈出一次整輪逾時警報。
2. 已取得結果保留；未開始通道為 NOTEST，已開始但未完成通道為 TIMEOUT。
3. 程式標記顯示待確認，上位機暫停後續動作。
4. 現場確認警報並處理既有結果衝突後，才允許上位機取用本輪結果。

## 程式核對所揭露的邊界

- 目前 STATION_SLOTS 將 DFU／FCT／BT 綁定為 7／6／4；KVM_BLOCK_COUNT 固定為七，與新容量及顯示需求不符。
- 未觀察到 Log 的位置不能一律推定為未放產品：Atlas、B482 BT 與 RS-WMT 現有的 NOTEST 判定條件不同。
- 核心目前以所有配置位置均進入終態判定整輪完成。整輪已有活動後，只有觀察到活動的個別位置才開始計算測試逾時；不能假設空位會自然逾時並完成本輪。
- 整輪 finished 後背景輪詢會退出；現有 B482 人工覆核只涵蓋部分不同來源檔案情境，KVM 仍顯示原結果，沒有待確認狀態。監控事件也未帶輪次識別；後續重構須處理跨輪事件歸屬，不能直接沿用彈窗就宣稱滿足新需求。

## 尚待釐清

- 未開始通道自動 NOTEST 的具體等待秒數；只有最終匯出資料的平台要如何避免過早定案，以及按下開始後建立快照所耗時間如何計入。
- 曾開始但缺最終結果的通道與整輪完全無活動的紀錄方式。
- 無法確認同輪來源能否由人工採用：使用者要求日後決定，不默認接受任一方案。
- 新 KVM 的定位標記與幾何尺寸；上位機對確認中狀態的處理方式。
- 配置匯入／部署流程、同一專案與機型的設備差異如何處理。
- 解析與判定規則邊界、驗收方式與遷移步驟。
