The current dashboard

The dashboard displays this round’s Log results for operators and KVM readers. Operators select a project and station type; engineers maintain configurations. Starting monitoring does not start the ATE. This guide follows the current source and actual Tk test windows.

Except for historical field photos in “Field comparison”, new images come from automated tests opening the actual App with isolated data and controlled logs or failures. SNs, paths and long messages are examples. These images do not certify production behavior or physical KVM capture.

Before starting

  1. Verify the App version, project/station type and readable Log folders.
  2. Check capacity and source-to-position mapping against the fixture. Capacity is not this round’s loaded quantity.
  3. Resolve pending reviews and startup faults. Handle persistence failures separately in recovery.
  4. Keep the fixed dashboard visible to KVM. Key events bring it forward without permanent topmost mode or forcing keyboard focus.

Run one round

  1. Select the project and station type. Ask an engineer to create a suitable configuration if missing.
  2. Press Start Monitoring（開始監控）or Command + Shift + M. Starting / Log preparation is BUSY: source baselines are not ready, so ATE must wait.
  3. Wait for monitoring readiness, then start the tester. Log collection and actual ATE testing are separate events; TESTING or a trusted result provides activity evidence.
  4. Check Slot, SN and status. One PASS does not release the round. All positions must be final, same-round evidence trusted, and required reviews resolved.
  5. Handle conflicts, alarms, cancellation or startup reset as appropriate. Explicitly start every new round; there is no automatic retest.

Observed in this test: In the controlled LI1 scenario, the round snapshot and independent marker enter monitoring while the footer can still read Preparing. Use this image to compare activity and markers; footer text alone must not authorize testing. Pause and report if reliable readiness for this round is missing.

Engineer configuration: edit, validate, apply

Open ⚙️ → Engineer Configuration（工程師配置）. A configuration contains project, station type, platform, capacity, source mapping, paths and three deadlines. This replaces the old station-and-path form.

  1. Load the configuration and check project/station, platform and capacity (1–20).
  2. Set source-to-display mapping, such as 1:1, 2:2, using the platform’s source numbering; do not infer it from visible row labels alone.
  3. Use Browse（選擇）for the required roots. Start wait, test limit and round limit are positive integer seconds.
  4. Validate Draft（驗證草稿）, then Apply and Save（套用並保存）. Validation alone does not save. Cancel leaves the draft unapplied; a failed save retains the effective configuration.
  5. Export portable configurations for deployment. After import, check local paths and the effective selection. Reload Deployed Configurations（重新載入部署配置）reads saved data; consider unapplied edits first.

The configuration is snapshotted at round start; later changes do not rewrite that round. Preferences and configurations are stored in ~/Library/Application Support/B518LogSolution/preferences.json.

DeadlineTiming and behavior
Start waitStarts when the round is accepted, including preparation. With no trusted activity or valid result anywhere, stop collection, finalize unstarted positions as NOTEST and request review. If some positions have activity, the remaining unstarted positions become NOTEST at deadline without claiming the entire tester never started.
Test limitStarts at each position’s first trusted activity; COMPLETING does not reset it. One position becomes TIMEOUT while others continue.
Round limitUses the common round start. If positions remain unfinished, stop collection, retain terminal results, finalize others as NOTEST/TIMEOUT by activity evidence and create a round alarm. When results are final and only conflicts remain, there is no review countdown.

Built-in/migrated defaults: DFU start/test 30/480 s; B518/FCT 120/480 s; BT 30/240 s. The default round limit is 7200 s. The selected configuration determines effective values and engineers may change them.

Slot results and KVM

StatusMeaning and next action
WAITINGNo trusted activity at this position yet; check tester start and paths.
TESTINGTrusted activity observed; verify SN and wait for final results.
COMPLETINGTransitional state while awaiting final results; may be brief and is not PASS.
PASS / FAILFinal platform result. FAIL can also mean Atlas activity ended before a trusted SN was read. Check round-level release separately.
NOTESTPlatform-declared no-test, or no trusted activity before deadline. Read source reasons in events; these are not interchangeable empty-fixture diagnoses.
TIMEOUTAn active position exceeded its limit; not product FAIL. Check late logs or a stalled tester.
STOPPEDAn unfinished position when monitoring was manually stopped. Existing PASS/FAIL/NOTEST/TIMEOUT results remain.

Current KVM layout

Each row has ten cells: capacities 1–10 use one row; 11–20 use two. Row one represents Slots 1–10 and row two 11–20. Out-of-capacity cells stay black; scrolling details does not move markers or cells. The old seven-cell mode is retired; readers must use the matching contract.

Separate state markers distinguish standby, preparation, monitoring, review, normal completion and releasable manual stop. READY does not imply PASS or available results; BUSY includes preparation and review. Product cells show per-position results: all green or retained previous results alone cannot authorize release.

Manual stop, cancellation and startup reset

SituationAction
Manual stop after monitoring readinessStop retains terminal results and marks unfinished positions STOPPED, preserving the manual_stop reason. Once all positions are final and reviews resolved, release is possible with a distinct manual-stop completion state. Operators decide rework scope.
Stop during preparation / readiness unverifiedVisible cells are insufficient for release. After the source returns and required handling finishes, explicitly cancel the round, retain its records and start again.
Cancel roundExplicitly abandon further release while retaining records. Cancellation does not delete data, convert it to FAIL or automatically retest.
Startup failureFix paths/permissions and choose Confirm and Reset Startup Fault（確認並復位啟動故障）. This ends the failed request or cancels the created failed round while keeping evidence. Reset never starts ATE; saved faults remain recoverable after restart.

Resolve conflicts and alarms

Same-round result conflict

When a position receives a candidate inconsistent with its locked result, the App keeps the original and requests review. Open ⚠️, select a candidate, and compare SN, status, source time, full paths and diagnostics. Matching filenames do not establish identical sources; scroll the original detail when needed.

  1. Confirm the selected candidate. Review multiple candidates individually.
  2. Adopt a new candidate only with trusted same-round evidence; otherwise keep the original. Missing same-round evidence cannot be overridden; controls reflect eligibility.
  3. Closing only dismisses the window. Reopen it with ⚠️; it does not release results.

Round alarm

No activity before the start deadline, or unfinished positions at the round deadline, stops collection and creates an alarm. This does not prove ATE hardware failure. Read the reason and results, address the issue and explicitly acknowledge. Acknowledgement may be disabled while preparation/finalization is pending. It resolves only the alarm, not other conflicts, and never starts a new round.

Notifications and persistence recovery

Open 🔔 for recovery. Notifications can include alarms and Session/audit/archive failures; inspect each tab’s reason and available action. Closing the window does not acknowledge anything; pending work remains available on reopening.

  1. Alarm tab: verify round_id and reason; acknowledge only that alarm.
  2. Save/archive tab: select a failed item, inspect diagnostics and retry. Persistence completeness and result release are separate; cell colors alone are insufficient.
  3. Verify recovery status after retry. If it still fails, retain the diagnostic information rather than masking the issue with another round.
  4. Closing waits for required writes. Failures keep a retryable close window available; cancel closing to return to handling. Canceling close is not round cancellation.

Historical events and App diagnostics

Historical queries read saved round and App events; they are not SN-based production/yield reports. Open history from Settings → Events and Session（設定 → 事件與 Session）. App diagnostics is also available from the dashboard.

  1. Select start/end dates and query. Read the first published batch while later batches may still be preparing.
  2. Navigate pages and select an event for details. A page still preparing is not evidence that no events exist.
  3. One query retains fixed content and order. Later events or cleanup do not silently rewrite published pages. Query again for current data.
  4. Cancel a query when needed. Retry failed later batches while published content remains readable. Inspect query diagnostics for degraded indexes, unreadable sources or invalid dates.
  5. Language changes preserve the query, page, selection and reading position; legacy text and raw diagnostics retain their originals.

App diagnostics

Inspect App events and raw reasons for persistence or text-refresh failures. Retry event saving or text refresh as appropriate; controls are disabled when nothing is pending. App diagnostics is separate from product test-failure analysis.

Round-record retention and cleanup

Set global retention days (a positive integer) in ⚙️ → Retention（保存期限）, and verify the effective saved value. Retention starts from trusted archival time, not the last viewing time. Active, pending-review, incompletely saved or untrusted archives are not ordinary expired rounds.

Read scan/delete/retain/failure counts and reasons in cleanup summaries. No data and cleanup failure are different. This manages the tool’s round records, excluding platform logs, configurations, preferences and manual exports. App events use the same global retention days but count from each original event time; rounds count from trusted archival time.

Report and retain evidence

Use Open Session Records（開啟 Session 紀錄）to locate the folder. Common files include session.json, events.log and results.csv; round audit evidence is persisted separately. Sessions do not copy platform logs. Attach original source logs and record time, version, project/station and round_id.
