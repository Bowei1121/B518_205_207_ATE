# Spec、開發票與獨立 PR 審查流程

這份文件是使用者確認的協作方式，適用Codex、Claude與Cursor等開發session。核心規則：寫完程式後，交由獨立session審查；有阻擋問題就回原實作session修正，同PR複查，直到對最新版建議合併。合併並確認本票完成後，才可開始下一張票。

## 六個階段與交付物

| 階段 | 做什麼 | 完成時留下什麼 |
| --- | --- | --- |
| 1 訪談 | grill-with-docs搭配bro，用白話釐清需求與例子 | 已確認的需求、詞彙與必要決策；未定案事項仍標示未定案 |
| 2 規格 | to-spec將討論轉成需求源頭 | 以「Spec：」開頭的父Issue、驗收條件、不做的範圍及來源對照 |
| 3 拆票 | to-tickets先提出可獨立驗收的拆法，經使用者確認再發布 | 每票為Spec子Issue，具有可交付行為、驗收條件與真正阻擋依賴 |
| 4 實作 | 新session使用implement處理一張可開始的票 | 工作分支、提交、測試證據、關聯子票的PR |
| 5 審查與修正 | 新的獨立session使用code-review審查；原session依PR留言修正，同PR複查 | 每輪審查的確切commit、可修正的問題、逐項回覆及最新版結論 |
| 6 合併與結票 | 最新版通過審查與必要驗證，並有合併授權時合併 | 合併結果、已完成的子票；之後才可進入下一票 |

前五階段的完成不等於已合併。即使兩票沒有依賴，使用者目前仍採逐票完成；同一票的多輪修正不算下一票。

## 角色與模型偏好

| 角色 | 使用者目前偏好 | 責任 |
| --- | --- | --- |
| 實作者／修正者 | Luna 6，High；implement技能 | 按Spec與子票實作、驗證、開PR及處理審查留言 |
| 獨立審查者 | Sol 6.1，Medium；code-review技能 | 對照需求、程式差異與證據，判斷是否建議合併 |

模型名稱是使用者選擇，不是品質保證；可用名稱與設定以實際session為準，看不到時記錄未知，不捏造或默換模型。由使用者建立新session並選擇模型；只有明確授權時才能使用相應工具代建或通知。skill文字本身不會切換模型，也不會在PR有留言時自動喚醒原session。

## Spec 與子票

Spec是需求源頭，子票定義本次完成哪一部分，PR記錄實際差異與證據。已有Spec或子票時先沿用，不因標題不同重複建立；「Spec：」命名用於新的父規格，不批次改名既有議題。

開始前檢查阻擋依賴、是否已有人認領、是否已有進行中的票或PR。ready-for-agent不代表前置依賴已完成。只處理使用者指定或已授權選取的一張可開始票；前票尚未合併時，不開始下一票。

若實作或審查發現需求矛盾，先列出差異與具體情境，交使用者決定。規格與測試不能被修改成剛好接受目前實作；確認的需求變更應回寫Spec與子票，再重新評估影響。

## 實作與開 PR

從最新整合分支建立或接續本票工作分支，遵守專案的分支前綴。保留他人未提交工作，先比較遠端差異；避免在整合分支直接推入產品變更。

完成本票可觀察行為與必要驗證後，自動提交並推送已授權的工作分支，開一個關聯本票的PR。PR至少說明：問題與結果、對應Spec／子票、修改範圍、實際測試及尚缺的驗證。使用Refs關聯票；開PR不代表可以關Issue。

若已經有本票PR，修正沿用同一PR，保持可追蹤。需要實機、KVM或其他外部條件的驗收，列出實際缺少什麼，不能以部分測試或語法檢查冒充完成。只有必要的驗證不足時才阻擋；可選的觀察不應擴張為所有票都必做的檢查。

實作session可自查，但不能替代獨立審查。完成PR後交接並停止本階段，不自行以「我看過沒問題」宣稱可合併。

## 獨立審查與留言

審查session先讀父Spec、子票、驗收條件、相關專案規則、PR現有討論與完整差異，取得目標分支與PR確切HEAD。由專案指定code-review技能執行時，沿用其規範／規格檢查方式；不能只看提交摘要或實作者宣稱的測試結果。

審查範圍包含：需求有無漏做、行為是否相符、既有流程是否被破壞，以及測試是否真能驗證該問題。實際執行過、只閱讀紀錄及尚未執行的驗證分開寫。沒有可證實的問題時，不為湊數提出猜測。

每個問題都要有：

- 明確標題與是否阻擋合併。
- 檔案／行號或可定位的差異位置。
- 觸發情境、目前行為及影響。
- 違反哪項需求／驗收條件，或具體回歸證據。
- 可供實作者處理的預期結果；必要時附重現方法。

在已授權發佈的指定PR寫入留言；可定位程式碼的問題優先用inline comment，整體結論放PR討論。只有聊天回覆，不能假裝PR已有留言。若只能讀取，先完成可審查的結論，再說明發佈受阻；不虛構留言連結。

每次結論固定記錄：

| 欄位 | 內容 |
| --- | --- |
| 審查版本 | PR HEAD完整commit；必要時包含基準commit與Spec／子票版本 |
| 結論 | 建議合併／不建議合併／必要驗證不足 |
| 阻擋問題 | 對應留言與尚未解決項目；沒有則明確寫無 |
| 驗證 | 實際執行與讀取的證據、缺少的必要驗證 |

審查中若HEAD變動，不把結論套用到未審查版本。記錄本次實際檢查的commit，並指出新版仍需複查。GitHub上的留言作者帳號可能相同，獨立性指開發與審查由不同session完成，不偽裝成另一個人或捏造審查者身分。

## 同 PR 修正與複查

原實作session重新讀取PR總結、inline comments及相關回覆，按阻擋問題修正並執行對應驗證，提交推送到同一工作分支。逐項回覆修正commit、改了什麼與如何驗證；不同意時提出具體理由與證據，交審查者判斷。

實作者不能自行把「已修改」當成「已通過」。問題是否解決由審查session確認；不以刪留言、刪測試或改Spec掩蓋問題。非阻擋建議可以另行記錄，不必為其擴張本票。

推送後交回獨立審查；審查者確認原問題並檢查修正引入的影響。任何HEAD改變，包括衝突解決或rebase，舊commit的建議合併結論都不自動沿用。持續「修正→複查」直到最新版通過；需求未定、必要設備／權限缺少或無法取得證據時如實停在未通過，不假裝完成。

## 合併條件

只有使用者已授權本次合併，且下列條件都成立，才能執行：

1. 最新的獨立審查對目前PR HEAD明確「建議合併」，而非舊版本的結論。
2. 所有阻擋發現已由審查者確認處理；必要的自動／人工驗收及專案CI要求均滿足。
3. 規格與本票範圍仍一致、前置依賴已完成、PR可正常合併。
4. 合併前再次讀取HEAD，仍與通過審查的版本一致；合併操作本身也必須帶入平台的expected SHA條件。GitHub CLI可用`--match-head-commit`綁定通過審查的完整commit，避免讀取後到合併前有人推送的競態。版本不符就停止並回到複查，不移除條件重試；工具不支援時不自動合併。

「建議合併」是品質結論，並非額外合併授權。既有明確合併授權可沿用，不重問；沒有授權時先把PR與證據準備完整再交給使用者。

合併後確認遠端PR確為merged、整合提交存在，再依授權關閉已完成子票；父Spec只在全部需求完成並驗收後才可結案。合併不表示所有未完成需求都已完成。

只在本票合併完成後，才可依使用者後續指示或既有順序執行授權開始下一票；不自行啟動另一session。若專案要求同步多個遠端，工作中同步同名工作分支；審查前不能以同步為名把它直接推成整合分支。核准合併後才同步同一整合結果。

## 直接使用的交接提示

這些是提示範本，不會自動建立session。補入實際Issue／PR連結，在新session選擇指定模型。

### 實作

使用 $issue-pr-review-loop 與implement技能處理我指定的子Issue。讀父Spec、前置依賴與驗收條件；完成實作、驗證及工作分支PR後交接獨立審查，先不要合併或關票。

### 審查

在新的獨立session，使用 $issue-pr-review-loop 與code-review技能審查我指定的PR。對照父Spec與子票，記錄確切HEAD，將具體問題與最終結論發佈到這個PR；不要修改產品程式、合併或關票。

### 修正

使用 $issue-pr-review-loop 讀取我指定PR的最新審查留言，在原工作分支修正、驗證、推送同一PR並逐項回覆；完成後交回獨立複查，不自行宣稱審查通過或開始下一票。

## 適用範圍

流程用於產品程式實作與審查。單純訪談、規格、拆票或建立此文件／skill，不代表已授權開始實作、審查、合併、監看、通知其他session或改平台權限。需要某項技能時先確認在該工具可用；其他工具若無自動skill載入功能，可明確指定讀取本文件，但不能宣稱已原生安裝。
